**Décisions (& pourquoi) :**
- **Packaging hatchling avec `packages = ["src/domain", "src/game", "src/config"]`** :
  `uv sync` installe le projet en editable → `import domain/game/config`
  fonctionne partout (manage.py, gunicorn, pytest) **sans aucune manipulation
  de `sys.path`**. C'est ce qui évite les hacks de chemin classiques du layout src/.
- **`manage.py` par défaut sur `config.settings.dev`, `wsgi.py`/`asgi.py` sur
  `config.settings.prod`** : la CLI locale est permissive, le serveur est sûr
  par défaut ; `DJANGO_SETTINGS_MODULE` reste surchargeable dans les deux cas.
- **dev sans variable requise / prod fail-fast** : `dev.py` a une SECRET_KEY
  insécure par défaut (un `.env` vide suffit pour bosser) ; `prod.py` lève
  KeyError au démarrage si `DJANGO_SECRET_KEY` ou `DJANGO_ALLOWED_HOSTS` manquent.
- **`DJANGO_SETTINGS_MODULE = config.settings.dev` dans la config pytest** :
  pytest-django configure Django pour tout le monde ; les tests `tests/domain`
  ne touchent jamais la BDD (aucun marker `django_db`), exigence « sans BDD » tenue.
- **Aucune config ruff/pyright/import-linter dans pyproject** : volontaire,
  c'est le périmètre du ticket #30 (les outils sont installés, pas configurés).

- Vérifier qu'un `.env` vide + `uv sync` + `uv run python manage.py check`
  fonctionne sur une machine fraîche (le CA « .env.example suffit »).
- ⚠️ **Footgun connu pour la Phase 1** : le modèle `User` custom
  (`game.accounts`) doit être créé **avant** tout `migrate` sur une base
